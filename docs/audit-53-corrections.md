## Revue du 1er octobre (après CI verte sur `34b5ba1`) — deux défauts corrigés

- **D1 — l'attestation pouvait remplacer un vendeur sans raison sociale.** Un accord figé sans identifiant ni raison sociale, sous un autre nom d'atelier, restait « attestable ». Désormais le nom figé doit être celui du profil : raison sociale si l'accord en porte une, sinon nom d'atelier ; un accord sans aucun nom n'est jamais attesté (`seller_changed` ⇒ nouveau devis, nouvel accord). Un accord dont l'entité est connue n'est jamais attestable ; après attestation, une facture sous une autre entité reste refusée.
- **D2 — un nouveau devis pouvait se déclarer historique.** Un `INSERT` explicite de `contract_epoch='pre_external_v1'` rouvrait l'acceptation directe. Le trigger refuse désormais tout `INSERT` hors `external_v1` (`contract_epoch_immutable`) ; seule la migration classe les devis existants.
- Reproduits d'abord par des tests en échec, puis corrigés : `ownClientSellerIdentity.test.ts` 19/19 ; PostgreSQL 17 réel 8/8 sur la migration modifiée.
- **Conséquence pour la recette qwf** (lecture seule) : les 5 accords de fixtures (`10074e0e`, `d25ddb10`, `b494c98d`, `7d19cf4a`, `0bbf584a`) n'ont aucun nom de vendeur figé, et `QA-AUDIT-1790849409185` porte le nom d'atelier fictif « Atelier QA », différent du profil de l'atelier de recette ; ce profil n'a pas non plus d'identifiant. Après migration, ils s'afficheront « Ajoutez l'identifiant au profil », puis « vendeur différent » : refus attendus, pas des défauts. Le parcours d'attestation **réussi** ne peut pas être démontré sur ces données sans fabriquer un accord ; il est prouvé en PGlite et PostgreSQL 17.
