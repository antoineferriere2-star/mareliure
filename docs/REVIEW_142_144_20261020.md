## #142 : ordre des événements et retrait du PDF

Tête relue : `8a920541b224a4342b12a858084446c4223c0f61`, fusion `9721dc6bd7923e6e7a3240e388fd46073be30b36`. Les deux fichiers de transport examinés sont identiques entre cette tête et la base de la revue.

**Verdict : aucun retrait de PDF référencé par une réservation confirmée reproduit dans les ordres testés. Une limite P2 persiste lorsque Storage refuse la suppression.**

`labelOrchestrator.ts:46–54` ne demande la suppression qu'après échec de `label_confirmed` et relecture d'un job `failed`. La transition SQL prend le verrou de ligne (`20261016100000_round_trip_label_resolution.sql:18`) ; elle n'autorise la confirmation que depuis `claimed` ou `ambiguous` (ligne 28). Un job constaté absent, donc `failed`, ne peut plus être confirmé par cette machine à états entre la relecture et le retrait. Le magasin retire exactement `<jobId>/label.pdf` dans le bucket privé (`roundTripLabelStore.server.ts:44–46`). Cette conclusion suppose le respect de cette machine à états ; elle ne couvre pas une écriture SQL administrative arbitraire.

La suite indépendante [pdf-orders.repro.test.ts](review-142-144-20261020/pdf-orders.repro.test.ts) exécute l'orchestrateur et les migrations dans PGlite, avec fournisseur et stockage simulés. Une requête vérifie après chaque scénario qu'aucun job confirmé ne référence un objet absent du stockage simulé.

| Ordre imposé | Résultat observé |
| --- | --- |
| Constat d'absence puis adoption | Adoption refusée avant enregistrement du PDF. |
| Adoption confirmée puis constat | Constat refusé ; PDF conservé. |
| Deux constats ayant lu simultanément `ambiguous` | Deux réponses de succès, une seule transition d'absence. |
| Constat pendant le téléchargement, puis enregistrement du PDF | Confirmation refusée ; retrait du PDF. |
| Constat après enregistrement, avant confirmation | Confirmation refusée ; retrait du PDF. |
| Adoption gagnant entre la lecture et la transition du constat | Le constat relit `confirmed` ; PDF conservé. |
| Suppression retardée après constat | Nouvelle confirmation SQL refusée ; aucun job confirmé privé de PDF. |
| Webhook pendant l'adoption, puis relecture fournisseur annulée | État final annulé ; PDF conservé comme archive. |
| Webhook après confirmation puis constat | Constat refusé sur le job annulé ; PDF conservé. |
| Confirmation SQL validée, accusé de réception perdu | Relecture `confirmed` ; erreur remontée, PDF conservé. |
| Erreur avant la confirmation SQL | Job encore ambigu ; PDF conservé pour résolution. |
| Storage refuse le retrait après constat gagnant | Réponse `review_required/job_failed`, mais PDF privé orphelin conservé. |

**P2 — échec de nettoyage masqué.** `discardPrivateLabel` remonte bien `label_discard_failed`, mais l'orchestrateur absorbe toute erreur avec `.catch(() => undefined)` (ligne 53). Le chemin observé n'enregistre ni signal d'échec de nettoyage ni reprise explicite. La réservation reste correctement en échec ; aucune fuite publique ni réservation confirmée sans PDF n'a été reproduite. En revanche, « le PDF est retiré » n'est pas garanti si Storage échoue. Correctif proposé : journaliser et rendre le nettoyage reprenable, sans réactiver le job ni supprimer le PDF d'un job confirmé. Aucun correctif produit inclus dans cette revue.

PGlite permet d'imposer des entrelacements à l'aide de barrières et d'exécuter les contraintes SQL réelles. Ce n'est pas une épreuve de concurrence entre deux connexions PostgreSQL natives, ni un essai du stockage Supabase ou des webhooks Sendcloud hébergés.

## #144 : garde-fou de droits des nouvelles tables

Tête relue : `c51357f0877377f63cb1acc9acbc7f1c0715a670`. Au moment de la revue, #144 est **fusionnée**, contrairement à l'état annoncé dans le brief. Fichier examiné : `src/marketplace/security/newTableGrants.test.ts`, non modifié.

**Verdict P2 : le garde-fou accepte plusieurs créations de tables sans décision explicite de droits.** Il repose sur une expression régulière exigeant une liste de colonnes entre parenthèses, ne reconnaît pas plusieurs formes PostgreSQL valides et peut prendre du texte pour une instruction `GRANT`. Cela ne démontre aucune exposition actuelle de données : dans les sondes ci-dessous, l'absence de `GRANT` laisse justement `authenticated` sans SELECT. C'est la couverture de la règle de développement qui est insuffisante.

Les sondes [grants-detector.repro.test.ts](review-142-144-20261020/grants-detector.repro.test.ts) appellent le détecteur réel puis exécutent chaque SQL dans PGlite et interrogent `has_table_privilege`.

| Cas manquant valide | Résultat du détecteur actuel |
| --- | --- |
| `CREATE TABLE public.build_notes OF public.qa_note` | Création sans liste de colonnes non détectée. |
| `CREATE TABLE public.build_notes AS SELECT 1 AS id` | Non détectée. |
| `CREATE UNLOGGED TABLE public.build_notes(id int)` | Non détectée. |
| `CREATE TABLE "public".build_notes(id int)` ; schéma et table tous deux entre guillemets | Non détectées. |
| Nouvelle partition `CREATE TABLE … PARTITION OF … FOR VALUES …` | Non détectée. |
| Faux `GRANT` dans un commentaire `/* … */` | Considéré comme une décision de droits. |
| Faux `GRANT` dans une chaîne SQL | Considéré comme une décision de droits. |
| `GRANT` sur `public.other_build_notes`, puis création de `public.build_notes` | Mauvais nom accepté par correspondance de suffixe. |
| Création, vrai `GRANT`, puis renommage | Accepté à bon droit : les ACL suivent la relation ; ce cas ne contourne pas les droits. |
| Création, renommage, puis vrai `GRANT` au nouveau nom | Faux positif : l'ancien nom est signalé malgré les droits du nouveau. |

`CREATE TABLE public.build_notes;` seul est **invalide dans PostgreSQL** : ce n'est pas un contournement valable. Deux sondes négatives le vérifient. Les formes `OF`, `AS` et `PARTITION OF` sont les cas pertinents sans liste de colonnes.

Correction proposée dans une PR distincte : analyser les instructions SQL avec gestion des commentaires, chaînes et identifiants cités ; couvrir les variantes de `CREATE TABLE` et suivre les renommages ; rejeter une forme non comprise plutôt que la laisser passer. Ajouter les cas ci-dessus en tests de non-régression, avec les bons résultats attendus après correction. Les tests présents ici caractérisent les défauts actuels ; leur réussite ne signifie pas qu'ils sont corrigés.
